# Feature: Safe & Stable Releases (App Store-ready release pipeline, pre-account)

## Goal

Give Hanahuac a repeatable, verifiable, documented release process that works **today** without a
paid Apple Developer account, and is pre-wired so that code signing, TestFlight, and App Store
Connect uploads can be switched on with a small, documented set of steps once the account exists.

"Safe and stable" means, concretely for this repo:

1. **Deterministic versioning** — one source of truth for the app version and build number, with a
   scripted bump procedure and version-tag consistency enforced by CI.
2. **Quality-gated release builds** — a release is only produced from a commit that passes the FULL
   quality bar (lint, full test suite, ODR/geo-pack validation, base-only bundle check) run
   synchronously at release time, not just the fast per-PR subset.
3. **Reproducible, inspectable artifacts** — every release produces an unsigned Release-configuration
   `.xcarchive` (and an unsigned `.ipa` where feasible without signing) with SHA-256 checksums,
   attached to a GitHub Release with generated notes.
4. **Traceability** — an annotated `v<semver>` git tag, a CHANGELOG entry, and a GitHub Release for
   every version.
5. **Switch-on readiness** — the signing/upload path exists in the pipeline as clearly-marked,
   cleanly-skipped placeholder steps gated on secrets/vars that do not exist yet, plus a
   `docs/releasing.md` runbook with an explicit "when the Apple Developer account exists" section.

## Scope

### In scope

1. **Versioning scheme + bump tooling**
   - Semantic versioning for `MARKETING_VERSION` (`X.Y.Z`); `CURRENT_PROJECT_VERSION` is a
     monotonically increasing integer build number, incremented on every version bump.
   - `project.yml` remains the single source of truth; a committed script
     (e.g. `scripts/bump-version.sh` or `.py`) + `just bump <major|minor|patch>` recipe updates both
     values and regenerates the Xcode project. Manual edits documented as discouraged.
   - Release tags: annotated `v<MAJOR>.<MINOR>.<PATCH>` on `main` only.

2. **Changelog**
   - `CHANGELOG.md` at repo root in Keep-a-Changelog style, seeded retroactively with a brief
     summary of the current (pre-release) state under an `[Unreleased]` section.
   - Release procedure: move `[Unreleased]` content under the new version heading as part of the
     version-bump PR. The release workflow FAILS if the tagged version has no matching
     `CHANGELOG.md` section (scripted check, e.g. `scripts/check-changelog.sh`).
   - GitHub Release notes: auto-generated by GitHub (`generate_release_notes`) PLUS the CHANGELOG
     section body.

3. **Release CI workflow** (`.github/workflows/release.yml`)
   - Triggers: push of tag `v*` AND `workflow_dispatch` with a `dry_run` input (dry-run performs
     everything except tag-consistency enforcement and Release creation/publication) so the
     pipeline can be proven green before the first real tag.
   - Jobs/steps (macos-15, mirroring existing workflow patterns; Nix/flake for lint tools as in
     lint.yml):
     a. **Version/tag consistency gate** — fail unless the tag equals `v` + `MARKETING_VERSION`
        from `project.yml` (skipped in dry-run).
     b. **Changelog gate** — fail unless `CHANGELOG.md` has a section for this version.
     c. **Full quality gates** — lint suite, xcodegen generate, full `xcodebuild test`
        (Mac Catalyst, as ci.yml does), `generate-geo-packs.py --check`, `verify-odr-packs.sh`,
        Release-config build + `verify-base-only-bundle.sh`. These run synchronously here because
        releases are rare — this does NOT add anything to the per-PR blocking path.
     d. **Unsigned archive** — `xcodebuild archive` with Release configuration and
        `CODE_SIGNING_ALLOWED=NO` producing `Hanahuac.xcarchive`; package an unsigned `.ipa`
        (zip of `Payload/Hanahuac.app`) where feasible; compute SHA-256 checksums for all artifacts.
     e. **GitHub Release** — create the release for the tag with generated notes + CHANGELOG body,
        attach `.xcarchive` (zipped), `.ipa`, and checksum file. Mark as prerelease when the tag has
        a prerelease suffix (e.g. `v1.1.0-rc.1`).
     f. **Signing/upload placeholders (disabled)** — clearly-marked steps/job for
        App Store Connect upload (TestFlight), gated on a repo variable
        (e.g. `vars.APPSTORE_UPLOAD_ENABLED == 'true'`) AND presence of the API-key secrets, so
        today they skip cleanly with an explanatory log line and the workflow still succeeds.
   - Workflow YAML must pass the repo's yamllint gate; permissions minimal
     (`contents: write` only where the Release is created); concurrency group per ref.

4. **Local release tooling (justfile)**
   - `just release-check` — run the full release quality bar locally (lint, test, geo-packs-check,
     verify-odr-packs, verify-base-only, changelog/version consistency).
   - `just archive` — produce the unsigned Release `.xcarchive` locally (per-worktree DerivedData
     conventions preserved).
   - `just bump <part>` — version bump as above.

5. **Documentation** — `docs/releasing.md`:
   - The versioning scheme, how/where versions live, bump procedure.
   - Step-by-step release runbook: bump PR (version + CHANGELOG) → merge via normal gate → tag →
     release workflow → verify GitHub Release + artifacts.
   - Release quality gates and what each protects.
   - A clearly-marked **"When the Apple Developer account exists"** section: exact switch-on steps —
     `DEVELOPMENT_TEAM`/`CODE_SIGN_STYLE` settings to add to `project.yml`, the exact secret names
     to create (App Store Connect API key id, issuer id, `.p8` key content), the repo variable to
     flip, the ExportOptions plist to add, and which placeholder steps become live (TestFlight
     upload, App Store submission). Includes the note that the exact upload tooling
     (`xcodebuild -exportArchive` + upload vs. fastlane) must be re-verified against current Apple
     tooling at switch-on time, not assumed.

6. **First proven run** — a green `workflow_dispatch` dry-run of `release.yml` on `main` (or the
   feature branch) demonstrating the pipeline end-to-end without publishing anything.

### Out of scope

- Anything requiring the paid Apple Developer account to EXECUTE: code signing, provisioning
  profiles, notarization, App Store Connect API keys/secrets creation, TestFlight distribution,
  actual uploads, App Store metadata submission. (Preparing disabled placeholders + docs for these
  IS in scope, per above.)
- App Store listing assets (screenshots, description, keywords) — separate feature.
- Release branches / backport strategy — tags-only model chosen (see Assumptions).
- Crash reporting / analytics / staged rollout infrastructure.
- In-app "what's new" UI or update prompts.
- Changing the existing per-PR CI gates in any way.

## Constraints

- **No paid Apple Developer account** — nothing in the delivered pipeline may require signing or
  Apple credentials to succeed; every Apple-credential-dependent step must skip cleanly.
- **CI cost split (blocking vs async)** — this feature adds ZERO new per-PR blocking checks. All
  new automation runs only on tag push or manual `workflow_dispatch`. The full (slow) quality bar
  runs synchronously within the release workflow only, which is acceptable because releases are
  rare and must not be cut from an unverified commit.
- **Action versions** — do not assume GitHub Action versions from training data; use the majors
  already pinned in this repo and verify current majors (marketplace / existing pins) during
  implementation.
- **Repo conventions** — allowlistable command shapes (no `cd &&`, no heredocs), Nix flake/direnv
  for tooling (no hardcoded /nix paths), new YAML must pass yamllint, new shell scripts must pass
  shellcheck, new Python must pass ruff.
- **Merge gate** — PRs merge via the normal CI + `code-owner-review` (SHA-bound) gate; nothing in
  this feature may bypass or weaken it.
- **Unsigned iOS archive risk** — an unsigned device (`generic/platform=iOS`) archive in CI may hit
  toolchain edge cases. Per the project's "verify external assumptions empirically" rule, the
  implementing story must prove the unsigned archive command works with a throwaway run BEFORE
  building the workflow around it. Documented fallback if a device archive is impossible unsigned:
  produce the unsigned Mac Catalyst Release archive + an unsigned device *build* artifact, and
  record in `docs/releasing.md` that the signed device archive activates with the account.

## Assumptions

User clarification was not performed because the user was unavailable for synchronous Q&A during
this run (per orchestrator instruction); the following assumptions were made instead and are
documented for review:

1. **Tags-only release model (no release branches).** Single-developer app with squash-merge trunk
   development; release branches add ceremony with no benefit at this stage. Every release is an
   annotated `v*` tag on `main`. Revisit if hotfix-on-old-version support is ever needed.
2. **SemVer starting from the existing `1.0`.** The first tagged release will normalize to
   three-component semver (`v1.0.0`); `MARKETING_VERSION` is updated to `1.0.0` as part of the
   first bump. Build number stays a simple monotonically increasing integer (App Store requirement
   is only uniqueness/increase per version train).
3. **CHANGELOG maintained manually via `[Unreleased]`, finalized at release time** rather than
   fully auto-generated from commits. Squash-merge PR titles feed GitHub's auto-generated release
   notes as a complement; a hand-curated CHANGELOG is more useful to end users and cheap at this
   project's release cadence.
4. **Release quality bar runs synchronously in the release workflow, including the "slow" ODR
   checks.** The fast-vs-async CI split protects per-PR latency; a release is rare and must not
   ship unverified, so ~30-45 min of tag-time CI is acceptable and adds zero per-PR cost.
5. **GitHub Releases are created published (not draft) for real tags**, with prerelease flag for
   suffixed tags; dry-runs create nothing. Rationale: there are no external consumers yet, and a
   failed gate prevents Release creation entirely, so drafts add a manual step with no safety gain.
6. **Unsigned artifacts are the deliverable for now.** An unsigned `.xcarchive`/`.ipa` cannot be
   installed on devices or submitted — that is fine; its purpose is proving the Release build path,
   pinning the exact bits of a version, and giving the signed pipeline a tested skeleton.
7. **`docs/releasing.md` (lowercase, in `docs/`)** rather than root `RELEASING.md`, matching the
   repo's existing docs layout (`docs/privacy-policy.md`, `docs/odr-packaging.md`, ...).
8. **Placeholder gating via repo variable + secret-presence checks** (e.g.
   `APPSTORE_UPLOAD_ENABLED` var, `APP_STORE_CONNECT_*` secrets) is the switch-on mechanism;
   creating the secrets is a human action at account time, consistent with the project rule that
   credential provisioning is human-performed.
9. **Mac Catalyst remains the CI test destination** (per existing ci.yml and the
   "CI UI tests on Catalyst" project note); the release archive targets iOS
   (`generic/platform=iOS`, unsigned) with the documented Catalyst fallback if unsigned device
   archiving proves infeasible (see Constraints).
