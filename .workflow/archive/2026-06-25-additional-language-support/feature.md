# Feature: Additional language support (8 new languages)

Slug: `additional-language-support`

## Summary

Add full, production-quality language support for eight new languages to the Hanahuac iOS app,
mirroring the established data-driven i18n architecture (catalog + downloadable ODR packs + per-language
progress) introduced by the `nahuatl-korean-language-support` and `downloadable-language-packs`
workflows. Every new language must appear in the picker with its native name, resolve correctly through
its fallback chain, track progress independently, and ship as a downloadable On-Demand-Resources (ODR)
pack. **REAL professional translations are in scope and required** for both UI strings (`.lproj`) and geo
content (countries, capitals, rivers, mountains, seas) — fallback-only wiring is NOT acceptable as
"done" except where a fallback is explicitly granted (see Fallback policy).

The eight languages:

| # | Code | Native display name | Fallback chain | Content requirement |
|---|------|---------------------|----------------|---------------------|
| 1 | `es-ES`   | Español (España)       | `[es-ES, es-MX, en]` | COMPLETE — no gaps |
| 2 | `ca`      | Català                 | `[ca, es-ES, en]`    | Best-effort; fallback permitted |
| 3 | `eu`      | Euskara                | `[eu, es-ES, en]`    | Best-effort; fallback permitted |
| 4 | `yua`     | Màaya t'àan            | `[yua, es-MX, en]`   | Best-effort; fallback permitted |
| 5 | `it`      | Italiano               | `[it, en]`           | COMPLETE — no gaps |
| 6 | `pl`      | Polski                 | `[pl, en]`           | COMPLETE — no gaps |
| 7 | `nl`      | Nederlands             | `[nl, en]`           | COMPLETE — no gaps |
| 8 | `sr`      | Српски (Cyrillic)      | `[sr, en]`           | COMPLETE — no gaps |

Total languages after this feature: 6 existing (en, fr, de, es-MX, ko, nah) + 8 new = **14**.

## Authoritative decisions (from user clarification)

1. **Spanish (Spain) `es-ES`** is a new distinct BASE language code, display name "Español (España)",
   delivered as a downloadable ODR pack (NOT bundled). It exists independently of `es-MX`.
   - **Default device-locale selection MUST stay `es-MX`.** A Spain-region device must continue to
     default to `es-MX`. `es-ES` is NEVER auto-selected from device locale; it is only used when
     explicitly chosen by the user in the picker, OR as the fallback target for `ca`/`eu`.
   - The current `AppLocale.matching(_:)` already maps every `es-*` locale to `.esMX`. That behavior
     MUST be preserved verbatim — do not add `es-ES` to the device-locale matching logic.

2. **REAL professional translations for ALL 8 languages are IN SCOPE** — UI strings AND geo content.
   The agents must author complete, professional-quality translations following the established content
   pipeline (bundled `name_<suffix>`/`capital_<suffix>` columns in countries/rivers/mountains/seas.json,
   from which per-language `<code>-geo.json` ODR packs are generated by
   `scripts/generate-geo-packs.py`).

3. **Per-language dimensions — ALL apply to EVERY new language:**
   - UI strings (`<code>.lproj/Localizable.strings`, ~85 keys)
   - Geo content (country names + capitals, river names, mountain names, sea names)
   - Downloadable ODR pack (ALL 8 are downloadable; NONE newly bundled — `en` and `es-MX` remain the
     only bundled base languages)
   - Picker entry with native name
   - Per-language progress (independent SwiftData `ReviewCard` / `DailyProgressSnapshot` rows keyed by
     locale rawValue)

4. **Fallback policy — only `ca`, `eu`, `yua` may rely on fallback for genuine content gaps:**
   - `ca`  → `es-ES` → `en`  (fallback permitted; author as much real Catalan as feasible)
   - `eu`  → `es-ES` → `en`  (fallback permitted; author as much real Basque as feasible)
   - `yua` → `es-MX` → `en`  (Yucatec Maya; fallback permitted; author as much real content as feasible)
   - `es-ES`, `it`, `pl`, `nl`, `sr` → MUST have COMPLETE content (UI + geo). Their chain resolves to
     English ONLY as an ultimate code-level safety net that, per acceptance, must never actually be hit
     because content is complete.
   - Note: `ca`/`eu`/`yua` chains intentionally route through a Spanish base (`es-ES` for ca/eu,
     `es-MX` for yua) before English — matching the established "partial language → Spanish → en" pattern
     (`fallsBackThroughSpanish`).

5. **Serbian script decision: Cyrillic (`sr`).** Rationale: Cyrillic is the official, constitutionally
   designated script of Serbia and the default for formal/published content; while Latin (`sr-Latn`) is
   heavily used in digital/everyday contexts, a quiz app presenting authoritative geographic names is
   best served by the official script. Use code `sr` (Cyrillic), display name "Српски", consistently.
   Document this rationale in code comments where the descriptor is defined.

6. **Yucatec Maya = `yua`** (ISO 639-3), display name "Màaya t'àan", fallback through `es-MX`.

7. **Out of scope** (no paid Apple Developer account): code signing, CloudKit/entitlements changes,
   App Store Connect uploads. **In scope and required:** authoring complete professional translations,
   ODR pack data + tagging in `project.yml`, tests, passing build/test/lint.

## Established architecture to mirror (do NOT redesign)

- **Language registry:** `Hanahuac/L10n/AppLocale.swift` (enum case per language) +
  `Hanahuac/L10n/LanguageCatalog.swift` (one `LanguageDescriptor` per language: code, displayName,
  fallbackChain, availability, odrTags). Catalog order MUST match `AppLocale.allCases`. Adding a
  language = add an enum case + a catalog descriptor; resolvers are catalog-driven, not per-language.
- **UI strings:** `Hanahuac/<code>.lproj/Localizable.strings` (~85 keys; copy `en.lproj` as the key set,
  translate values). Resolution via `Hanahuac/L10n/L10n.swift` walking `fallbackChain`.
- **Geo content source of truth:** `Hanahuac/Resources/countries.json` (`name_<suffix>`,
  `capital_<suffix>`), `rivers.json` / `mountains.json` / `seas.json` (`name_<suffix>` only). Add a new
  suffixed column per language. Pick a clear suffix per code (e.g. `es_es`, `ca`, `eu`, `yua`, `it`,
  `pl`, `nl`, `sr`).
- **ODR geo packs:** generated by `scripts/generate-geo-packs.py` (extend `PACK_LANGUAGES` and
  `SUFFIX_BY_CODE`) → `Hanahuac/Resources/<code>-geo.json`. Verified in CI by `just geo-packs-check`.
- **ODR packaging:** `project.yml` — add each `<code>.lproj` and `<code>-geo.json` as resources tagged
  `[lang-<code>]`, and add both to `excludes` so they are not bundled. Regenerate via `just generate`.
- **Pack delivery seam:** `LanguagePackProvider` (bundled + ODR providers) is catalog-driven; new
  languages flow through automatically once catalog + packs + tags exist. Bundled provider must still
  build in-memory packs for new languages from bundled source for the offline/base path.
- **Per-language progress:** `ReviewCard` / `DailyProgressSnapshot` keyed by `language` (AppLocale
  rawValue); `CardStore` / `ProgressStatsStore` already filter by language — no model change expected,
  but tests must confirm isolation for new locales.
- **Picker:** `Hanahuac/Views/Settings/LanguagePickerView.swift` iterates `AppLocale.allCases` — new
  languages appear automatically with download UX from `downloadable-language-packs`.
- **Build/recipes:** `just generate` (xcodegen), `just geo-packs`, `just geo-packs-check`,
  `just verify-odr-packs`, `just verify-base-only`, `just lint`, `just test`, `just build-mac`.

## Acceptance criteria

1. All 14 languages (6 existing + 8 new) appear in the language picker, each with its correct NATIVE
   display name (es-ES "Español (España)", ca "Català", eu "Euskara", yua "Màaya t'àan", it "Italiano",
   pl "Polski", nl "Nederlands", sr "Српски").
2. Selecting each new language resolves UI strings and geo names correctly through its declared fallback
   chain (verified by tests for each chain in §Fallback policy).
3. `es-ES` exists as a distinct base language code, separate from `es-MX`, with display name
   "Español (España)".
4. Device-locale default selection is UNCHANGED: every `es-*` device locale still resolves to `.esMX`;
   `es-ES` is never auto-selected. (Regression test asserting `AppLocale.matching(Locale(identifier:
   "es_ES"))` == `.esMX`.)
5. Per-language progress is independent per locale for all new languages (ReviewCard /
   DailyProgressSnapshot isolation test covering at least one new locale).
6. Downloadable ODR packs build for all 8 new languages: `<code>.lproj` + `<code>-geo.json` exist,
   are tagged `[lang-<code>]` in `project.yml`, excluded from the bundle, and pass `just geo-packs-check`
   and `just verify-odr-packs` (DATA-ONLY). None of the 8 is bundled; `en`/`es-MX` remain the only
   bundled base languages.
7. **Content completeness:** `es-ES`, `it`, `pl`, `nl`, `sr` have COMPLETE professional translations for
   all ~85 UI keys AND all geo content (every country name+capital, every river/mountain/sea name) — no
   reliance on fallback. `ca`, `eu`, `yua` have professional translations to the extent feasible with
   their permitted fallback safety net. A test (or check) verifies the five complete languages have no
   missing UI keys and full geo coverage.
8. Catalog/enum invariants hold: every `AppLocale` case has exactly one `LanguageDescriptor`; catalog
   order matches `AppLocale.allCases`; bundled base languages carry no ODR tags; downloadable languages
   carry `[lang-<code>]`.
9. `just lint`, `just test`, `just geo-packs-check`, `just verify-odr-packs`, and an iOS/Catalyst build
   all pass. CI is green on the PR.

## Notes / risks

- Translation volume is large (8 languages × ~85 UI keys + ~195 countries + capitals + rivers/mountains/
  seas). break-stories should split by language and/or by dimension to keep stories independent and
  reviewable; group the five "complete-content" languages so completeness checks are enforceable.
- Authoring translations is expected to be done by `implement-story` directly (no new agent file), to
  avoid the workflow-tooling-in-worktree split. If a new agent in `.claude/agents/` is genuinely added,
  it must land in the PRIMARY checkout, not this worktree (Step 0 guard).
- Keep `AppLocale.matching(_:)` unchanged for `es-*` (es-MX default). Only add new enum cases there for
  codes that should auto-detect (it, pl, nl, sr, ca, eu, yua may auto-detect their own device locale;
  es-ES must NOT). Confirm desired auto-detect behavior per language during story design but never let
  es-ES auto-select.
